指南 13 — 官方用例食谱

目标： Cognition 官方文档里已验证的用法模式，整理成食谱——什么活该切给 Devin，以及 40+ 个带可复制 prompt 的文档化配方。 级别： 入门（广度篇） 来源： Best Practices · Use-case gallery · use-case tutorials

统领一切的那条规则#

官方指导，原话逻辑：挑 wide & shallow（宽而浅）的活——一大池简单、可水平扩展的任务永远胜过复杂的全新构建。

理想任务 反面任务
初级工程师复杂度的重复性子任务 全新的复杂功能
每片 < 90 分钟人工量 拆不开的东西
客观的通过/失败验证 "看着对就行"
隔离、向后兼容、可并行 纠缠的依赖

文档点名的四种最佳切片形态：迁移、重构、现代化、技术债积压。

食谱目录#

以下全部是官方 gallery 里的文档化用例——每个都带可复制 prompt。按"它从人一周里拿走什么活"组织。

事故与生产健康#

配方 机制
自动调查 Datadog/PagerDuty 告警 Webhook/API 触发 → 会话起火即查
自动生成 postmortem PagerDuty 关闭 → Devin 起草时间线、根因、行动项
每日修 Sentry 新错误 每晚 cron 拉新错误 → 早上有修复 PR
端到端调试 bug 报告 把报告 + Datadog 日志 + DB 权限交给 Devin → 根因

定时卫生（文档里 ROI 最高的一页）#

配方 节奏
每周依赖更新 PR 每周：过期包 → 已测试升级 PR
每晚跑 staging E2E 每晚：跑套件、失败建工单
每周从已合并 PR 生成 changelog 周五：分类 changelog → Slack
每日 Datadog 健康摘要 每日：错误扫描 → Slack 摘要
每日设计系统审计 每日：标记已合并 PR 里的硬编码颜色/缺失 token
Feature-flag 清理 发布后一次性会话剥掉 flag + 死代码
每周 Notion 状态摘要 每周：PR/commit 汇总 → Notion
从会议记录生成 PR 每小时：轮询 Granola → 提取工程任务 → 子会话

代码质量#

配方 机制
合并前自动修 PR bug Devin 审每个 PR，把修复推到分支
给服务补单测 建一个写测试 skill，套用到收费/退款/webhook 流程
抓视觉回归 repo skill：PR 前对每个受影响页面截图
每个 PR 跑迁移检查清单 repo skill 抓破坏性操作、校验 schema 变更
拆巨型 router 2,000 行 Express router → 按域拆路由共享中间件
提覆盖率 Devin 分析测试套件、写测试补缺口
跨 repo 修已知 CVE 官方 skills（devin-vuln-fixes）：只读盘点 → 审批门 → 确认版本补丁 → 前后测试 → 每 repo 一个 PR

让 Devin 自己变更好（"Devin Optimization"）#

配方 教训
功能 prompt 从 42→12 ACU 解剖一个昂贵会话：3 个根因 → 重写 prompt
3 个会话赛跑一个问题 并行会话竞速不同优化策略；最好的上线
一夜 8 个并行会话 8 个无测试模块 → 早上有单测 PR
评估 30 个库 每库一个会话 → 打分排序对比
把 hotfix 提炼成 skill 从一次成功的事故会话抽出可复用 skill
每周知识去重 定时会话合并/清理知识建议
团队上手指南 Devin 读自己的文档 → 按你技术栈写入门指南

怎么用这本食谱#

  1. 从定时卫生挑一个——最便宜的首胜（一个你不用再过脑的每晚/每周循环）
  2. 有 PagerDuty/Datadog/Sentry 就加一个事故配方
  3. 某个配方起效后，冻结成 skill（第 12 篇）或 Bot（第 1–5 篇）——上表每一行都能以这两种形态存续

实录演示 —— 一条食谱真跑一遍，录于 Devin CLI v3000.14（swe-2-flash-medium）#

拿「代码质量」栏里的 Raise code coverage 食谱端到端跑了一遍：一个小仓库里放着故意少测的 orders.py（折扣码、运费档位、边界条件）。prompt 只有一行，剩下的全交给 Devin。

视频（74 秒，无声）： 食谱 prompt → 读文件 → 写测试 → 命令审批 → 全绿。

1. swe-2-flash-medium 上的 CLI REPL——Pro 方案，免费档

2. 食谱 prompt 已提交——Devin 先读 orders.py 和 test_orders.py

3. 写测试——+43 行覆盖空购物车、折扣码、每个运费档

4. 命令审批——python3 -m unittest -v test_orders.py 等一个 Allow

5. 11 个测试全过——每个原先未测的分支都被点名；orders.py 未动、零提交

6. /exit 后验证——Ran 16 tests ... OK，改动按指令未提交

验证#

  • [ ] 有一个卫生循环 recipe 在按计划运行，并产出了第一个 PR/报告
  • [ ] 它的产出物已固化成 skill、playbook 或 Bot——不活在某个人的脑子里

常见陷阱#

  • 十个 recipe，零个固化。 停留为手动 prompt 的 recipe 到周五就被遗忘——要么固化要么扔掉。
  • 复制 prompt 却没换验证。 gallery 的 prompt 默认你有测试套件；要改的是检查，不只是任务。

自检#

  1. 为什么先从定时卫生循环入手而不是事故响应？（最便宜的胜利——睡觉时也在跑，错误的深夜 lint 修复可恢复，错误的事故操作不可恢复。）
  2. 「把 recipe 固化成 skill 或 Bot」实际防止了什么？（prompt 漂移和单人依赖——写出它的人走了，recipe 还活着。）
  3. 为什么先改 gallery prompt 的验证部分再改任务部分？（任务描述意图；检查才是你的仓库真正能证明的东西——错检查产出自信的垃圾。）
