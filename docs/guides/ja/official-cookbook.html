ガイド 13 — 公式ユースケース・クックブック

目標: Cognition 公式ドキュメントで実証済みの使用パターンをクックブックとして整理 — Devin に切り分けるべき仕事とは何か、そしてプロンプト付きでコピーできる 40 以上の文書化レシピ。 レベル: まずは網羅性のためにここから 出典: Best Practices · Use-case gallery · use-case tutorials

すべてを貫く唯一のルール#

公式ガイダンスのロジックをそのまま言うと:wide & shallow(広く浅い)仕事を選べ — シンプルで水平方向にスケールするタスクの大きなバックログは、複雑な新規構築に常に勝る。

理想的なタスク アンチタスク
ジュニアエンジニア程度の複雑さの反復的サブタスク 新規の複雑な機能
スライスあたり手作業 90 分未満 分割不可能なもの
客観的な合否検証 「なんか良さそう」
分離され、後方互換で、並列化可能 絡み合った依存関係

ドキュメントにある 4 つの優れたスライス形:マイグレーション、リファクタ、モダナイゼーション、技術的負債バックログ。

レシピカタログ#

以下はすべて公式ギャラリーに文書化されたユースケース — それぞれコピペ可能なプロンプト付き。人間の週から取り除いてくれる仕事別に整理。

レシピ 仕組み

ポストモーテムの自動生成 PagerDuty 解決 → Devin がタイムライン・根本原因・アクションアイテムを起草

バグレポートの end-to-end デバッグ レポート + Datadog ログ + DB アクセスを Devin に渡す → 根本原因

定期ハイジーン(ドキュメントで最も ROI の高いページ)#

レシピ 頻度

ステージングでの夜間 E2E 夜間:スイート実行、失敗分をチケット化
マージ済み PR からの週次変更履歴 金曜:分類済み変更履歴 → Slack

Devin 自体の上達("Devin Optimization")#

レシピ 教訓

30 ライブラリの評価 ライブラリごとに 1 セッション → スコア付きランキング比較

週次のナレッジ重複排除 定期セッションがナレッジ提案をマージ・競合整理
チームオンボーディングガイド Devin が自社ドキュメントを読む → あなたのスタック向け入門ガイド

このクックブックの使い方#

  1. 定期ハイジーンから 1 レシピ選ぶ — 最も安い初勝利(考えなくても回り続ける夜間/週次ループ)
  2. PagerDuty/Datadog/Sentry があれば インシデントから 1 つ追加
  3. レシピが動いたら スキル(ガイド 12)か Bot(ガイド 1–5)に凍結する — 上の行すべてはどちらかの形で生き残る

実録ウォークスルー — レシピを1本実演、Devin CLI v3000.14（swe-2-flash-medium）で収録#

Code quality 棚の Raise code coverage レシピを端から端まで実行：意図的にテスト不足にした orders.py（割引コード、送料ティア、エッジケース）を持つ小さなリポジトリで。プロンプトは一行、あとは Devin 任せ。

動画（74 秒、無音）： レシピプロンプト → ファイル読込 → テスト作成 → コマンド承認 → 全パス。

1. swe-2-flash-medium の CLI REPL — Pro プラン、無料枠

2. レシピプロンプト送信 — 最初に orders.py と test_orders.py を読む

3. テスト作成 — +43 行で空カート・割引コード・全送料ティアを網羅

4. コマンド承認 — python3 -m unittest -v test_orders.py が Allow を待つ

5. 11 テスト全パス — 未テストだった全ブランチを列挙；orders.py 無変更、コミットなし

6. /exit 後に検証 — Ran 16 tests ... OK、変更は指示どおり未コミット

検証チェックリスト#

  • [ ] ハイジーンレシピ 1 つがスケジュールで動き、最初の PR/レポートを出した
  • [ ] その出力がスキル・プレイブック・Bot に凍結されている — 誰かの頭の中に住んでいない

落とし穴#

  • レシピ 10 個、凍結ゼロ。 手動プロンプトのままのレシピは金曜には忘れられる — 運用化するか捨てるか。
  • 自社リポジトリの検証なしのコピペプロンプト。 ギャラリーのプロンプトはテストスイートの存在を前提にしている;タスクだけでなくチェックを適応させる。

理解度チェック#

  1. なぜインシデント対応より先に定期ハイジーンレシピから始めるのか?(最も安い勝利だから — 寝ている間に回り、夜間 lint 修正の失敗は回復可能だが、インシデント操作の失敗は回復不能だ。)
  2. 「レシピをスキルか Bot に凍結する」とは実際に何を防ぐのか?(プロンプトドリフトと個人依存 — レシピは書いた人を越えて生き残る。)
  3. なぜタスク部分より先にギャラリープロンプトの検証部分を適応させるのか?(タスクは意図を記述するだけ;チェックこそが自社リポジトリが実際に証明できるもの — 間違ったチェックは自信満々のゴミを生む。)
