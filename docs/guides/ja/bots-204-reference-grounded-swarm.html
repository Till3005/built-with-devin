ガイド 5 — 参照基盤スウォーム

目標： エージェントの群れに大規模で検証可能なシステムを書かせる——正しさを雰囲気ではなく信頼できる参照に対して継続的にチェックする。 レベル： 上級 出典となる導入事例： Harvey の 「Phil」——約 30 のエージェントが Rust + TypeScript で Word 互換の共同編集エンジンを記述：3 週間で 100 万行超、人間のエンジニア 0 人。実際の Microsoft Word の挙動とシミュレートされた弁護士の交渉に対して継続検証。人間はメモリ + 決定ログを通じて操縦し、コードは一切読まなかった。 出典： Gabe Pereyra のローンチ記事（@gabepereyra 経由）· ローンチ記事

パターン#

出力が正しいか誰も判定できないとき、スウォームは失敗する。Phil が機能したのは、すべての行が真実の参照——本物の Microsoft Word——に対して検査できたから。エージェントチームの仕事は発明ではなく一致——客観的で継続的に検査可能な目標。

   参照システム（真実）
            ▲ 比較
            │
┌───────────┴────────────┐
│  約30体のエージェント群   │──► 100万行超（Rust + TypeScript）
└────────────────────────┘
            ▲ 操縦
            │
   人間：メモリ + 決定ログ
   （コードは読まない）

適用場面#

向いている 向いていない
仕様の再実装（ファイル形式、プロトコル、エディタ、コンパイラ） 客観的な答えのないグリーンフィールド製品
オラクルのある移植/移行（旧システムがまだ動く） 「正しさ」が判断問題である新規 UX
動作中システムと diff 可能なあらゆるもの 正しさの判定にユーザーが要るシステム

リトマス試験：機械があなたなしに「正しい」を決定できるか？ できればスウォームはスケールする；できなければプロダクトオーナー Bot（ガイド 2）を使う。

ステップ 1 — 先に参照を確保する#

どのエージェントがコードを書くより前に、チェックが存在しなければならない：

  • Harvey の参照：本物の Microsoft Word の挙動——スウォームのエディタでレンダリングした文書が Word と一致する必要があった
  • あなたの場合：まだ稼働している旧システム、適合性スイート、ゴールデンファイル、仕様テスト集、API 契約

比較を CI かスウォームが常時走らせるスクリプトに組み込む——「出力が参照と一致するか」は安価で自動でなければならない。さもないとエージェントはチェックとチェックの間に漂流する。

ステップ 2 — 所有されるスライスに分解する#

約 30 のエージェントは一つのバックログを共有しなかった——各エージェントがサブシステム（文書モデル、レイアウトエンジン、共同編集プロトコル…）を所有するよう作業が切り分けられた。ガイド 4 の組織図と同じ構造だが、すべての「従業員」がモジュール境界を向いたコーディングセッション：

You own the <module>. Its contract is <interface/reference behavior>.
Your PRs are accepted when the reference checks pass — not when the
code looks done.

ステップ 3 — 人間はコードの上から操縦する#

Harvey の誰も 100 万行を読まなかった。操縦は以下を通じて行われた：

  • メモリ——Bot が蓄積した、下された決定とその理由の事実
  • 決定ログ——分岐ごとにスウォームが選んだもの
  • 方向メッセージ——「今週はパフォーマンスより変更履歴の忠実度を優先」

あなたのレビュー対象は diff ではなく決定の軌跡。生成コードを読んで状況を把握しようとしている自分に気づいたら、オーケストレーターに決定ログを求める。

ステップ 4 — 上に敵対的検証を重ねる#

Harvey は第 2 のチェックを重ねた：シミュレートされた弁護士の交渉——適合性スイートが見逃すものを浮かび上がらせる現実的な使用。あなたの等価物：参照 diff の上のシナリオ層——実ワークフロー、敵対的入力、ファジング。参照チェックは誤りを捕らえ、シナリオチェックは脆さを捕らえる。

検証チェックリスト#

  • [ ] 自動化された参照チェックが存在し、すべての変更に対して走る
  • [ ] 各エージェントの受入基準が「コードを書いた」ではなく「参照が通る」
  • [ ] コードを読まずにログ/メモリから「スウォームが何をなぜ決めたか」を答えられる
  • [ ] 意意図的に壊したモジュールがあなたではなく参照チェックに捕捉される

落とし穴#

  • オラクル以前のスケーリング。 チェックのないスウォームは量を産むだけ——Phil が機能したのは Word が常に審判だったから。
  • diff のレビュー。 エージェント約 2 体を超えるとスケールしない；あなたがボトルネックになり、スウォームの速度優位を失う。
  • 曖昧な所有。 2 体のエージェントが 1 つのモジュールを編集するとマージ地獄になる——所有の境界こそがアーキテクチャ。

理解度チェック#

  1. 大抵のマルチエージェント試行が崩壊する中、なぜ Harvey のスウォームは機能したか？（信頼できる外部参照——実際の Word の挙動——が正しさをスウォーム速度で機械検査可能にした）
  2. なぜ人間はコードレビューではなくメモリと決定ログで操縦したか？（3 週間の 100 万行超は人間の読解容量を超える；操縦は意図の層で起こる）
  3. このパターンを試す前に確認すべき前提は？（あなたのドメインに、スウォームが自己検査できる参照があるか——なければ先にオラクルを作る）
